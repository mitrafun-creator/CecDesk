# Процесс разработки и ролевой бизнес-процесс CecDesk

Этот документ задаёт единый «коробочный» процесс разработки между **Бизнесом** (владелец продукта) и **Командой** (роли внутри AI-инженерии и локальный учёт задач на ПК).

---

## 1. Роли в системе

| Роль | Кто исполняет | Зона ответственности |
| --- | --- | --- |
| **Бизнес (Product Owner)** | Автор проекта (пользователь) | Ставит задачи, описывает хотелки и баги, определяет приоритеты (`P0`–`P3`), согласовывает спорные UX/архитектурные решения и принимает результат. |
| **Поддержка и Аналитик (Support & BA)** | Команда | Разбирает входящие запросы, логи/архивы `cecdesk_support_*.zip`, находит первопричину, переводит хотелку в чёткое ТЗ с **критериями приёмки (Acceptance Criteria)** и регистрирует задачу в [`pm/TASKS.md`](../pm/TASKS.md). |
| **QA / Тестировщик** | Команда | До начала кода готовит тест-кейсы и список регрессионных рисков (Windows, SteamOS, RP2040-Zero, ESP32-S3, миграция конфигов); после кода выполняет проверки и выносит вердикт `PASS / FAIL`. |
| **Тимлид / Архитектор (Tech Lead)** | Команда | Проектирует чистое решение без дублирования и костылей, проверяет границы модулей, совместимость и безопасность. |
| **Разработчик (Dev)** | Команда | Реализует изменения в Rust (`src-tauri`), WebUI (`ui/`) и прошивке (`firmware/`), добавляет модульные тесты. |
| **Релиз-инженер (Release Manager)** | Команда | Ведёт [`CHANGELOG.md`](../CHANGELOG.md), контролирует SemVer-версию и SHA-256 через `release_tool.bat`, готовит патч-ноуты и GitHub Releases. |

---

## 2. Пайплайн прохождения каждой задачи (6 этапов)

Любая ваша идея, доработка или баг-репорт проходит один и тот же цикл:

```text
[Бизнес: идея / баг]
        |
        v
1. [Поддержка / Аналитик]: Triage & Spec -> карточка в pm/TASKS.md (статус SPEC)
        |
        v
2. [Тимлид + QA]: Архитектура, риски, тест-план -> статус READY FOR DEV
   (если требования неоднозначны или ломают UX — короткое согласование с Бизнесом)
        |
        v
3. [Разработчик]: Код + Unit-тесты + документация -> статус IN QA
        |
        v
4. [QA]: Автотесты, clippy, сборка/бинарная гигиена, проверка Edge Cases -> PASS / FAIL
   (при FAIL возврат на этап 3)
        |
        v
5. [Релиз-инженер]: Запись в CHANGELOG.md ([Unreleased]), обновление статуса задачи -> DEMO
        |
        v
6. [Бизнес]: Приёмка и (при необходимости) запуск релиза через release_tool.bat gate
```

---

## 3. Жизненный цикл статусов в `pm/TASKS.md`

- `INBOX` — сырой запрос от Бизнеса.
- `SPEC` — Аналитик оформил суть, компонент и критерии приёмки.
- `IN_DEV` — Тимлид и QA согласовали план и тест-кейсы; Разработчик пишет код.
- `IN_QA` — код готов, идёт проверка тестами и сборкой.
- `READY` — QA дал `PASS`, изменения внесены в `CHANGELOG.md` (`[Unreleased]`), ждёт показа/приёмки Бизнесом.
- `DONE` — принято Бизнесом и/или вошло в конкретный релиз.

---

## 4. Правила качества (Definition of Ready & Definition of Done)

### Definition of Ready (можно брать в код)
1. Понятна цель (зачем Бизнесу/пользователю эта задача).
2. Заданы проверяемые критерии приёмки (Acceptance Criteria).
3. Учтены обратная совместимость (`CEC-EMU`, старые конфиги, Portable-режим) и обе ОС (Windows / SteamOS).

### Definition of Done (задача может считаться завершённой)
1. Код и тесты написаны без дублирования логики; существующие комментарии/документация не сломаны.
2. Запущены и пройдены **после финальной правки**:
   - `node --test tauri_app/ui/js/catalog.test.js` (при изменениях UI/i18n/каталога);
   - `run_clippy.bat` и `run_tests.bat` (при изменениях Rust);
   - `pio run` (при изменениях `firmware/`).
3. Изменение отражено в `CHANGELOG.md` (`[Unreleased]`) и в [`pm/TASKS.md`](../pm/TASKS.md).
4. Отчёт Бизнесу содержит только реально проверенные файлы, команды и результаты без вымысла.
